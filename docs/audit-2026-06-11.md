## Confirmed findings (22) — adversarially verified

### [HIGH] Per-asset `Asset.ips` set is uncapped and uncounted — a local-IP flood (IPv6 link-local needs no setup) grows one asset's IP set without bound, defeating the constant-memory guarantee

**Where:** `src/analysis/assets.rs (lines 570-583 (insert at 581); reached from observe() 747-758; is_local IPv6 547-550)` · **Dimension:** alloc-dos

`Asset.ips: BTreeSet<IpAddr>` (assets.rs:93) is the one growable collection with NO entry in `analysis::Limits` and NO overflow counter. The unbounded path is `record_local_host` (assets.rs:570-583), which unconditionally does `asset.ips.insert(ip)` (line 581) on the MAC-keyed asset. In `observe()` it is called right after `bind()` whenever `is_local()` is true:

  if self.is_local(src_ip) {
      self.bind(pkt.eth.src, src_ip);          // caps ip_to_mac at max_bindings, may DROP
      self.record_local_host(pkt.eth.src, Some(src_ip), ts);  // ALWAYS inserts into asset.ips
  }

Crucially, `record_local_host` runs even when `bind()` already dropped the IP at the `max_bindings` cap — so the `max_bindings` cap does NOT bound `asset.ips`. The single MAC-keyed asset is created once (counted once against `max_assets`), so `asset_mut(AssetKey::Mac(mac))` never trips the asset cap on subsequent packets. The only thing growing is that one asset's `ips` set, which has no per-asset bound (there is no `max_ips_per_asset`).

Trigger (no setup required, IPv6): `is_local` returns true for ANY IPv6 link-local/ULA address with no subnet learning and no cap (assets.rs:547-550: `(seg[0] & 0xFFC0) == 0xFE80 || (seg[0] & 0xFE00) == 0xFC00`). `ip_pair()` returns Some for a bare IPv6 frame with no transport (decode/mod.rs:88). So an attacker sends Ethernet(14)+IPv6(40) ~54-byte frames, all with one constant unicast src MAC and a fresh `fe80::<random 64-bit>` src address each. Every frame passes `is_unicast` + `is_local`, and inserts a new `IpAddr` into the single asset's `ips` set. With 2^64 link-local addresses available the set grows until OOM. IPv4 variant: one crafted DHCP ACK with mask 255.0.0.0 learns 10.0.0.0/8 as local (`is_plausible_netmask` permits /8, assets.rs:313-318), then frames from 16.7M source IPs in 10/8 inflate the same set.

This breaks two stated guarantees at the mission-critical bar: (1) the `Limits` doc claims 'every collection is entry-capped below' and degradation is reported with 'an honest dropped N counter' (analysis/mod.rs:26-38) — `ips` is neither capped nor counted, so the drop is silent; (2) the reader's headline 'constant memory on any file size' / `gzcat big.pcap.gz | pincer assets -` streaming promise (pcap/mod.rs:6-8, 156-161) is defeated, because resident memory now grows with the streamed file rather than staying constant. At render the set is materialized a second time: render_assets builds `asset.ips.iter().map(ToString).collect()` then `ips.join(", ")` (output/mod.rs:382-388), a single multi-hundred-MB String, and the JSON path serializes the whole BTreeSet — roughly doubling/tripling peak. (Not rated critical only because the retained-to-wire ratio is ~1:1 rather than super-linear; it is still an uncounted, unbounded path that can OOM a fixed-RAM sensor on a streamed hostile capture.)

**Evidence:**

```
src/analysis/assets.rs:580-582:
        if let Some(ip) = ip.filter(|ip| !ip.is_unspecified() && !ip.is_multicast()) {
            asset.ips.insert(ip);
        }

src/analysis/assets.rs:751-754 (record_local_host runs even if bind dropped at the cap):
            if self.is_local(src_ip) {
                self.bind(pkt.eth.src, src_ip);
                self.record_local_host(pkt.eth.src, Some(src_ip), ts);
            }

src/analysis/assets.rs:547-550 (IPv6 link-local/ULA always local, no learning, no cap):
            IpAddr::V6(v6) => {
                let seg = v6.segments();
                (seg[0] & 0xFFC0) == 0xFE80 || (seg[0] & 0xFE00) == 0xFC00
            }

Limits has no max_ips_per_asset (src/analysis/mod.rs:40-49): max_flows, max_assets, max_bindings, max_subnets, max_hostnames_per_asset, max_services_per_asset, max_dns_records, max_dhcp_records — none bounds Asset.ips.

AssetOverflow has no `ips` field (src/analysis/assets.rs:238-249) — the drop cannot even be reported.
```

**Recommendation:** Add a `max_ips_per_asset` to `Limits` (and a tiny() value) plus an `ips: u64` field on `AssetOverflow`, then route every `asset.ips.insert` through a capped helper mirroring `add_hostname`/`add_service`: insert only while `asset.ips.len() < cap`, otherwise increment `overflow.ips` and drop. Apply it at all four insert sites (assets.rs:149 extend in merge_from, 524 promote, 581 record_local_host, 660 DNS-answer). Surface `overflow.ips` in the `Degradation` envelope (output/mod.rs:110-129) and the stderr warning so the drop is counted, not silent. A generous default (e.g. 4096 IPs/asset) leaves real multi-homed hosts unaffected while restoring the bounded-memory and constant-memory guarantees.

### [HIGH] DNS/mDNS answer attribution is unauthenticated: a crafted record poisons any victim IP's inventory hostname (forensic poisoning into SIEM)

**Where:** `src/analysis/assets.rs (lines 650-663)` · **Dimension:** dns-answer-attribution-trust

The AppEvent::Dns arm in observe_app attributes the answer-record NAME to the asset that owns the answer-record's CLAIMED IP, with no trust gating whatsoever. For each A/AAAA answer it computes key=self.key_for_ip(answer-claimed-IP), inserts that IP onto the asset, and calls attribute_hostname(key, answer.name, ...). Both the IP (RDATA) and the name are fully attacker-controlled bytes parsed straight out of the packet by src/app/dns.rs (A at line 141 `DnsRData::A(rd.ipv4()?)`, name at line 168 `summary.answers.push(DnsAnswer { name, data })`). Three checks present elsewhere are ABSENT here:

1) dns.is_response is never consulted. It IS parsed — src/app/dns.rs:57 `pub is_response: bool` set at line 100 `is_response: flags & 0x8000 != 0` — but observe_app ignores it. A QUERY packet (qr=0) that simply carries answer records in its answer/additional section is processed identically to a response. parse_inner walks the record section whenever qd_count<=MAX_QUESTIONS regardless of qr (dns.rs:114 `for index in 0..record_total`), so any attacker datagram, even one shaped as a question, can carry poisoning A-records.

2) No relationship is required between the packet's source IP (the responder/speaker) and the A-record's claimed IP. There is no check that the responder is authoritative for, on-segment with, or even equal to the claimed IP. An attacker at 10.0.0.66 can emit a record `attacker.example IN A <domain-controller-IP>` and the DC's asset (whether MAC- or IP-keyed via key_for_ip at line 399) gains the hostname `attacker.example` and gains the claimed IP via `asset.ips.insert(ip)` (line 660).

3) The name is stored at full trust grade. source_for (line 722) yields NameSource::DnsAnswer or NameSource::Mdns; NameSource ordering (line 22-28: Dhcp, Mdns, DnsAnswer, Tls, Http) makes Mdns rank ABOVE DnsAnswer, Tls and Http, and display_name()/the primary name reported to the SIEM picks min-by-source (line 183-187 `min_by_key(|(_, src)| **src)`). So an mDNS-grade poisoned name will WIN over a legitimate TLS/HTTP-derived name on the same asset and become the displayed identity.

This is a direct trust-boundary inconsistency: the SAME packet's *service* attribution at line 824-832 IS gated (`!dns.is_mdns && udp.src_port == 53 && is_unicast(src)` plus key_for_ip(src) — it credits the SPEAKER, not a claimed third party), and the DHCP arm (608-648) is carefully gated (only DhcpMsgType::Ack binds, only yiaddr is trusted, relayed/giaddr exchanges rejected, OFFER and option-50 client claims distrusted). The hostname arm received none of that scrutiny.

mDNS makes it strictly worse: mDNS is unauthenticated multicast that any host on the segment may emit, sniffed on UDP 5353 (src/app/mod.rs:97 `dns::parse(udp.payload, true)`), and its names rank second-highest in NameSource so they win the display name. A single multicast frame can rewrite a neighbor's reported identity.

**Evidence:**

```
src/analysis/assets.rs:650-663:
```
AppEvent::Dns(dns) => {
    // A/AAAA answers name the *server* IP; attribute to its asset.
    for answer in &dns.answers {
        let (ip, source) = match &answer.data {
            DnsRData::A(ip) => (IpAddr::V4(*ip), source_for(dns.is_mdns)),
            DnsRData::Aaaa(ip) => (IpAddr::V6(*ip), source_for(dns.is_mdns)),
            _ => continue,
        };
        let key = self.key_for_ip(ip);
        if let Some(asset) = self.asset_mut(key, ts) {
            asset.ips.insert(ip);
        }
        self.attribute_hostname(key, answer.name.clone(), source, ts);
    }
}
```
No `dns.is_response`, no `pkt.ip_pair()` source check, no on-segment check. Contrast the gated service arm 30 lines below, src/analysis/assets.rs:824-831:
```
if let (AppEvent::Dns(dns), Some((src, _))) = (event, pkt.ip_pair())
    && let Some(TransportView::Udp(udp)) = &pkt.transport
    && !dns.is_mdns
    && udp.src_port == 53
    && is_unicast(src)
{
    let key = self.key_for_ip(src);   // credits the SPEAKER, not a claimed IP
    self.attribute_service(key, 53, "udp", ServiceEvidence::AppLayer, ts);
}
```
is_response parsed but unused: src/app/dns.rs:57 `pub is_response: bool,` / dns.rs:100 `is_response: flags & 0x8000 != 0,`. Display name picks most-authoritative source, src/analysis/assets.rs:183-187:
```
pub fn display_name(&self) -> String {
    self.hostnames
        .iter()
        .min_by_key(|(_, src)| **src)
        .map_or_else(|| self.key.to_string(), |(name, _)| name.clone())
}
```
NameSource ordering puts Mdns above DnsAnswer/Tls/Http, src/analysis/assets.rs:22-28.
```

**Recommendation:** Gate the hostname-attribution arm with the same rigor as the service arm and the DHCP arm:

1) Require dns.is_response before attributing any answer record (drop answer records riding on queries). For mDNS, require it to be an mDNS response (qr=1) as well.

2) Require a relationship between the responder and the claimed IP. The conservative, defensible rule that mirrors the existing service arm: only attribute a name when the A/AAAA record's claimed IP equals (or is on the same learned local segment as) the packet's source IP — i.e. trust a host to name ITSELF, not to name arbitrary third parties. For unicast DNS, additionally require udp.src_port == 53 and is_unicast(src) as the service arm already does. For mDNS, require the announcing source to be the claimed IP (mDNS announces are self-claims; key off pkt.ip_pair() source rather than the RDATA IP).

3) If cross-host attribution must be retained for resolver-style records, introduce a distinct, lowest-trust NameSource grade (rank it BELOW Tls/Http, not above) so a poisoned DNS/mDNS name can never become an asset's primary display_name and can be filtered/flagged by the SIEM as untrusted-grade. Carry the untrusted grade through the JSON envelope so downstream consumers can distinguish self-asserted vs. third-party-asserted names.

4) Add a property/integration test asserting that (a) a query carrying A-records attributes nothing, and (b) a response from host A claiming `evil IN A <host-B-IP>` does not attach `evil` to host B's asset.

### [HIGH] SPB records get fabricated epoch timestamps with zero degradation signal — forensic timeline silently falsified

**Where:** `src/pcap/pcapng.rs (lines 376-395)` · **Dimension:** reader-equivalence-skew

parse_spb constructs every Simple Packet Block record with `ts: Timestamp::ZERO` (pcapng.rs:390) because the SPB carries no timestamp. Nothing downstream distinguishes this sentinel from a real 1970-01-01 timestamp: Stats min/max folds it in (stats.rs:77-78), every flow's first_ts/last_ts starts and stays at ZERO (flows.rs:102, 331-332), and every asset's first_seen/last_seen does too (assets.rs:134-135). The result is rendered as fact in the summary table ('from 1970-01-01T00:00:00.000000Z'), in summary JSON (first_ts/last_ts/duration_secs at output/mod.rs:166-181), and in flows JSON (first_ts/last_ts at output/mod.rs:201-202). Empirically verified: the SAME logical 2-packet capture re-encoded four ways gives identical JSON for legacy-us/legacy-ns/pcapng-EPB, but the pcapng-SPB encoding reports duration 0.000s, from/to 1970-01-01, and flow first_ts/last_ts of 1970-01-01 — while stderr is empty and the JSON degradation envelope is all zeros. That envelope is documented as 'all zeros means the analysis was complete' (output/mod.rs:106-110), so a SIEM or forensic pipeline is affirmatively told the data is trustworthy. SPBs are produced by real high-rate capture tools (SPB exists precisely to minimize per-packet overhead), so this is a legitimate-producer path, not only an attack: an analyst correlating pincer flow times against logs gets a 56-year-wrong timeline with no warning. The Degradation struct (output/mod.rs:111-129) and warn_degradation (cli.rs:286-337) have no field or message for timestamp-less records — this violates the project's own 'silent degradation is the failure mode a NASA-grade tool must not have' contract (cli.rs:285).

**Evidence:**

```
pcapng.rs:389-394: `Some(Record { ts: Timestamp::ZERO, orig_len, link_type: iface.link_type, data })`. Empirical run on the same frames: `pincer summary ng_epb.pcapng` → 'duration 100.000s / from 2001-09-09T01:48:20.000001Z'; `pincer summary ng_spb.pcapng` → 'duration 0.000s / from 1970-01-01T00:00:00.000000Z / to 1970-01-01T00:00:00.000000Z' with empty stderr and JSON degradation `{truncated_tail: false, undecodable_records: 0, skipped_blocks: 0, ...all zeros}`. flows --json on the SPB file: `192.168.1.10:54321 -> 192.168.1.1:53 1970-01-01T00:00:00.000000Z 1970-01-01T00:00:00.000000Z` vs the correct 2001 timestamps from the EPB/legacy encodings.
```

**Recommendation:** Make timestamp absence explicit instead of a ZERO sentinel: either change Record.ts to Option<Timestamp> (pcap/mod.rs:59) or have the pcapng reader count SPB/timestamp-less records the way it counts skipped_blocks. Then (1) exclude timestamp-less records from Stats first_ts/last_ts and from Flow/Asset first/last updates so those fields stay None rather than epoch; (2) add a `timestampless_records: u64` field to Degradation (output/mod.rs:111-129) wired through Pass/degradation() (cli.rs:341-357); (3) emit a stderr warning in warn_degradation ('N Simple Packet Block(s) carry no timestamp; time fields and duration are unavailable'); (4) render '-'/null for unknown times instead of 1970-01-01.

### [MEDIUM] Cap admission is first-come-first-served, so the surviving asset/flow/binding set is a function of packet arrival order, not the set of packets — the stated order-independence/determinism guarantee breaks the moment any analysis::Limits cap engages (the hostile case)

**Where:** `src/analysis/assets.rs, src/analysis/flows.rs (lines assets.rs:558-568, 447-482, 487-505, 346-366; flows.rs:316-326)` · **Dimension:** determinism-under-caps

pincer's headline guarantee is deterministic, snapshot-testable, reproducible forensic output (DESIGN.md:24 'Reports must be diff-able and snapshot-testable'; DESIGN.md:313 record_provisional/finalize 'is what makes the inventory order-independent'). That guarantee is verified only for the SUB-CAP case: tests/invariants.rs proves order-independence with DEFAULT limits and no cap hit (service_evidence_is_insertion_order_independent at invariants.rs:163-210, syn_flow_direction_is_order_independent at 113-155, asset_key_resolution_is_stable at 213-226). tests/hostile.rs proves caps BOUND memory and COUNT drops, but never that the surviving set is identical across permutations of the same capture.

Every cap in the system admits whichever identities/keys are observed FIRST and refuses the rest, so the result depends on order:

1. asset_mut (assets.rs:558-568): `if !self.assets.contains_key(&key) && self.assets.len() >= self.limits.max_assets { ...; return None; }` — once the map holds max_assets entries, any NEW identity is dropped. The surviving asset set is the first max_assets distinct keys seen.
2. bind (assets.rs:460-464): `let known = self.ip_to_mac.get(&ip).copied(); if known.is_none() && self.ip_to_mac.len() >= self.limits.max_bindings { ...; return; }` — the first max_bindings IPs to be bound win; later local IPs are denied an authoritative binding and therefore stay IP-keyed instead of MAC-keyed.
3. record_provisional (assets.rs:494-500): same first-N-wins cap on the provisional map that finalize() later resolves.
4. flows.rs observe (316-326): `Entry::Vacant(e) => { if len >= self.limits.max_flows { self.dropped += 1; return; } ... }` — the first max_flows distinct FlowKeys survive; the rest are dropped.

finalize() (assets.rs:346-366) iterates `self.provisional` in BTreeMap (IP-sorted) order, which is deterministic GIVEN a fixed provisional set — but the set itself is order-dependent because of cap #3, and the bind() calls inside the loop can additionally hit cap #2. BTreeMap ordering guarantees stable iteration of WHATEVER survived; it does nothing to make WHAT survives order-independent.

Because deps (src/analysis/deps.rs:39-108) is derived from flows + the inventory's key_for_ip resolution, and the DOT/JSON renderers consume assets()/by_bytes()/dependency_edges(), all three downstream artifacts inherit the divergence: two SIEM ingests of the same hostile capture, or the same capture replayed with reordered packets (e.g. merged/re-sorted pcapng, multi-interface capture), yield different inventories, different top-conversations, and different dependency graphs. At the mission-critical/hostile-input bar this defeats reproducibility and diffability precisely when the input is adversarial — the situation the caps exist for.

**Evidence:**

```
Proven empirically with a throwaway integration test against the public API (AssetInventory/FlowTable::with_limits(Limits::tiny()), observe, finalize, assets/iter/key_for_ip), feeding the SAME packet set forward vs. reversed:

FLOWS (20 distinct dst-port flows, max_flows=8):
  forward survivors:  [1000,1001,1002,1003,1004,1005,1006,1007]
  reversed survivors: [1012,1013,1014,1015,1016,1017,1018,1019]

ASSETS (20 distinct off-link server IPs via DNS A answers, max_assets=8):
  forward:  [203.0.113.0 .. .6, 8.8.8.8]
  reversed: [203.0.113.13 .. .19, 8.8.8.8]

IP->MAC KEYING (20 distinct local hosts on a learned /16, on data frames, max_bindings/provisional=8):
  forward:  hosts .0-.6 are Mac-keyed, .7-.19 stay Ip-keyed
  reversed: hosts .0-.12 stay Ip-keyed, .13-.19 are Mac-keyed
The SAME host (e.g. 10.0.1.0) is reported as a MAC-identified device in one order and as a bare IP in the other — its very identity, and thus every dependency edge touching it, flips with arrival order.
```

**Recommendation:** Make the survivor set a deterministic function of the packet SET, not arrival order, for the cap-engaged path. Options, strongest first: (a) Order-independent eviction: when a cap is hit, choose survivors by a total order on the key itself (e.g. keep the numerically/byte-smallest max_N keys), so the surviving set is identical across any permutation. This requires evicting an already-admitted larger key when a smaller new key arrives — bounded extra work, BTreeMap makes 'largest current key' O(log n). (b) Count-only-no-drop within the snapshot is not viable here (it would reintroduce the unbounded growth the caps prevent), but a two-pass variant is: in pass 1 record only the SET of keys (cheap, still capped by a deterministic key-ordered eviction), in pass 2 populate stats only for survivors. (c) At minimum, if deterministic eviction is rejected, document loudly in DESIGN.md and the degradation report that 'once a cap engages, output is no longer reproducible across packet reorderings' and add a proptest that permutes a cap-exceeding capture and asserts the CURRENT (order-dependent) behavior, so the limitation is explicit and regression-guarded rather than implied-absent. Also extend tests/invariants.rs with a forward-vs-reversed permutation test under Limits::tiny() — today no test exercises determinism under caps at all.

### [MEDIUM] gen follows symlinks and silently overwrites at predictable filenames (TOCTOU/symlink write)

**Where:** `src/cli.rs (lines 410-418)` · **Dimension:** io-cli

run_gen writes each scenario with std::fs::File::create(&path) where path = out_dir.join("office.pcap"|"incident.pcap"). File::create opens with O_CREAT|O_TRUNC and FOLLOWS an existing symlink at the destination, truncating and writing the link's target. There is no O_NOFOLLOW/O_EXCL, no existence check, and no prompt. The destination filenames are fixed and the documented invocation (`cargo run -- gen testdata`, run routinely because a test enforces byte-identity of the committed samples) targets a predictable path. An attacker who can plant a symlink at testdata/office.pcap (a shared/CI checkout, a world-writable out_dir) redirects the write to an arbitrary file the running user can write — e.g. a config, key file, or build script — clobbering it with pcap bytes. Even absent an attacker, a user's real capture they happened to name office.pcap is overwritten with no warning.

**Evidence:**

```
let path = args.out_dir.join(name);
let file = std::fs::File::create(&path).map_err(|e| Error::output(&path, e))?;  // follows symlink, O_TRUNC, no prompt

Verified: symlink gendir/office.pcap -> victim.txt; `pincer gen gendir` reported `wrote gendir/office.pcap` and victim.txt became a 'pcap capture file' (original 'PRECIOUS DATA' gone). Plain file ow/office.pcap with 'real capture I care about' was silently replaced (exit=0).
```

**Recommendation:** Open destinations defensively: create with create_new(true) (O_EXCL) and only overwrite after an explicit --force flag, or open with O_NOFOLLOW (e.g. via OpenOptions + a nofollow custom flag on unix) so a symlink at the path is rejected rather than followed. At minimum, refuse to overwrite an existing non-regular-file (symlink) and document the overwrite behavior in the gen help text.

### [MEDIUM] Degraded/truncated/capped runs carry no in-band signal for DOT and table output and never change the exit code

**Where:** `src/cli.rs (lines 279-402)` · **Dimension:** io-cli

Degradation (truncated tail, undecodable records, skipped pcapng blocks, flow/asset/dns/dhcp caps, MAC rebinds) is reported on only two channels: a best-effort stderr warning (warn_degradation) and, for --json, the `degradation` envelope (degradation()). The DOT path (deps --dot) returns deps_dot(&edges) through write_stdout with no degradation argument, and the table path (emit -> report.to_table()) likewise renders no degradation. The process exit code is identical (0) for a clean run, a truncated capture, and a cap-saturated run — run() returns Ok(()) in all of these. A downstream automation consumer that captures stdout (a saved/piped DOT graph fed to Graphviz, or a parsed table) into a SIEM and gates on exit code will treat a capture that was truncated mid-file or had millions of flows dropped as a complete, successful analysis. This contradicts the code's own stated goal ('Silent degradation is the failure mode a NASA-grade tool must not have', cli.rs:285) for every output mode except JSON.

**Evidence:**

```
// deps --dot bypasses the envelope entirely:
if args.dot && !args.common.json { return write_stdout(&deps_dot(&edges)); }
// table path never receives degradation:
fn emit(report: &Report<'_>, json: bool, degradation: &Degradation) { let rendered = if json { report.to_json(degradation)? } else { report.to_table() }; ... }

Verified: `pincer deps trunc.pcap --dot` produced DOT with 0 degradation/truncated/partial markers in stdout; warning appeared only on stderr. `pincer summary trunc.pcap`, `--json`, and `--dot` all exited 0 (same as a clean run).
```

**Recommendation:** Make degradation detectable without scraping stderr on every path: emit a DOT comment line (e.g. `// pincer: PARTIAL — truncated capture; N flows dropped`) and a table footer when any Degradation field is nonzero, and/or return a distinct nonzero exit code (or honor a --strict flag that does) when results are degraded so exit-code-driven pipelines can branch on partial analysis.

### [MEDIUM] Mid-stream BadMagic/BadVersion from a second SHB discards the entire analysis

**Where:** `src/cli.rs (lines 206-215 (with src/pcap/pcapng.rs:93-97, 133-135))` · **Dimension:** parsing-bounds

The record loop deliberately degrades on mid-stream TruncatedFile/BadLength ('stop and report what we have, flagged') but any other PcapError returns Err, discarding every packet already analyzed. In pcapng, a concatenated capture whose SECOND section header has a corrupt BOM yields PcapError::BadMagic (pcapng.rs:96), and a second SHB with major != 1 yields PcapError::BadVersion (pcapng.rs:133-135) — both reachable mid-stream via State::read_section_header_after_len called from next_record's BLOCK_SHB arm (pcapng.rs:183-195). One damaged or crafted trailing section therefore suppresses the full report for everything that parsed cleanly before it, contradicting the code's own stated bar ('A sensor that throws away an hour of evidence over a bad tail is worse than one that says partial'). ### [LOW] pcapng Section Header body is allocated to the attacker-declared length (up to 64 MiB) as a fresh, non-reused Vec

**Where:** `src/pcap/pcapng.rs (lines 116-117)` · **Dimension:** alloc-dos

`read_section_header_after_len` allocates `let mut body = vec![0u8; body_len];` where `body_len = total_len - 16` and `total_len` is attacker-controlled, bounded only by `MAX_RECORD_LEN` (64 MiB, pcapng.rs:107-108). Unlike the per-packet path, this allocation does NOT reuse the streaming `buf` — it is a fresh heap Vec each time an SHB is parsed, and SHBs recur in concatenated multi-section captures (each SHB resets endianness/interfaces and re-enters this path via next_record at pcapng.rs:183-195). A hostile file consisting of many SHBs each declaring `total_len` near 64 MiB therefore forces repeated 64 MiB transient allocations. Impact is bounded: `read_exact` (pcapng.rs:117) requires those bytes to actually be present, so the file must contain ~64 MiB per SHB, and the Vec is freed after parse (only version + trailer length are consulted). So it is bounded by input size and transient, not retained — but it is an allocation sized to a declared length that the reader otherwise never needs to hold in full.

**Recommendation:** The SHB body is only read for the 4-byte version field and the 4-byte trailing length; it does not need to be buffered whole. Either reuse the streaming `buf` (as the EPB/SPB path does at pcapng.rs:214-217) instead of a fresh Vec, or read just the version word and skip the remainder of the declared body without materializing it, so a large SHB length cannot drive a large allocation.

### [LOW] Lossy non-injective '?' sanitization lets distinct on-wire names collapse and be forged

**Where:** `src/app/mod.rs (lines 37-43)` · **Dimension:** output-injection

### [INFO] Unchecked integer addition outside the arithmetic_side_effects deny in is_plausible_netmask

### [INFO] IPv6 atomic fragments (offset 0, M=0) are flagged 'fragmented', slightly skewing UDP truncation accounting

**Where:** `src/decode/ipv6.rs (lines 87-101 (with src/decode/mod.rs:172-179))` · **Dimension:** parsing-bounds

The fragment-header arm sets `fragmented = true` for any fragment header without reading the M flag (LSB of offset_flags). RFC 6946 atomic fragments — offset 0, M=0, a complete datagram wrapped in a fragment header — are therefore classified as 'first fragment of a fragmented datagram'. The only behavioral consequence is in decode_packet's truncation accounting: for first fragments the UDP payload_truncated signal is deliberately suppressed (mod.rs:172-179, 'the missing bytes live in the other fragments'), so an atomic-fragment UDP packet whose length field overstates the captured payload is counted as clean rather than truncated. No memory-safety, framing, or transport-parsing impact: transport parsing still happens (offset is 0) and the payload remains cursor-bounded. Documented fragment limitations cover reassembly, not this M-flag classification nuance, hence recorded at info.

**Recommendation:** Read the M flag: `let more = offset_flags & 1 != 0;` and set `fragmented = more || offset_flags >> 3 != 0;` so atomic fragments keep honest UDP truncation accounting. One-line change plus a fixture test with an atomic-fragment UDP packet whose length field lies.

### [INFO] SPB padding bytes can reach decoders when orig_len lies high

**Where:** `src/pcap/pcapng.rs (lines 376-394)` · **Dimension:** parsing-bounds

parse_spb derives the captured length as min(orig_len, snaplen, remaining) and its comment asserts the derivation exists so we do 'NOT hand the padding bytes (up to 3) to the decoders as if they were packet'. That holds for spec-conforming writers, but orig_len is attacker-controlled: if orig_len overstates the real captured data while staying under snaplen, `remaining` is the padded body length, so up to 3 padding bytes are included in Record::data and handed to the decoders as packet bytes. Practical impact is nil — an attacker who controls the file controls all packet bytes directly, and IP-layer total_length bounds usually exclude the trailing bytes anyway — so this is recorded only because the code comment claims a guarantee slightly stronger than the code provides.

**Recommendation:** Soften the comment to 'padding is excluded for spec-conforming writers; a lying orig_len can include up to 3 pad bytes, bounded by the IP length fields downstream', or, if exactness is wanted, no fix is possible (SPB genuinely carries no cap_len) — the comment is the only thing to change.

### [INFO] parse_epb/parse_spb interface fallbacks silently decode under default link type if the well-formed pre-check ever drifts

**Where:** `src/pcap/pcapng.rs (lines 361-365 (and 383))` · **Dimension:** parsing-bounds

packet_block_well_formed rejects EPBs whose interface_id is undeclared (pcapng.rs:289) and SPBs in sections with no IDB (pcapng.rs:280) — precisely to avoid decoding under guessed defaults. Yet parse_epb still falls back to `unwrap_or_default()` (Ethernet link type, microsecond clock, 64 MiB snaplen) and parse_spb to `interfaces.first().copied().unwrap_or_default()`. Both fallbacks are dead code today because the pre-check runs first (pcapng.rs:247), but the invariant connecting the two functions is implicit: if a future edit reorders the loop or weakens the pre-check, packets on undeclared interfaces would silently decode with the wrong link type and clock instead of being skipped and counted — exactly the failure mode the pre-check's comment warns about ('would otherwise decode under guessed defaults (wrong link type, wrong clock)').

**Recommendation:** Make the dead path fail loudly instead of guessing: have parse_epb return Ok(None)/an error when interfaces.get() is None (and parse_spb when first() is None), or replace unwrap_or_default with a comment-anchored `else { return ... }`. This turns the cross-function invariant into local code.

### [INFO] SHB-context BadLength errors report file offset 0

**Where:** `src/pcap/pcapng.rs (lines 110-114, 145-149)` · **Dimension:** parsing-bounds

Both BadLength constructions inside read_section_header_after_len hard-code `offset: 0`. For the initial SHB that is correct, but the same function is called mid-stream for concatenated sections (pcapng.rs:192), so a bad second-section SHB reports 'at byte offset 0' when the damage is megabytes in. CaptureReader carefully threads a real offset for every other error site ('Byte offset into the file, for error reporting', pcap/mod.rs:78-79), so this is a diagnostics accuracy gap only — no parsing or safety impact.

### [INFO] DepEdge carries 5 owned Strings per edge (key strings, labels, proto) — duplicated identity strings dominate deps memory at scale

**Where:** `src/analysis/deps.rs (lines 11-25, 80-98)` · **Dimension:** perf-scale

Each aggregated edge eagerly stores client/server key Strings (AssetKey::to_string), two label String clones, and a proto String, even though edge identity is already the Copy (AssetKey, AssetKey, u16, IpProto) map key. With a hostile distinct-edge flood the edge count approaches max_flows (2M), i.e. up to 10M heap Strings duplicating data resolvable from the inventory at render time. Measured: `deps` on 500k flows/~500k edges peaked at 690MB RSS vs 439MB for `flows` (table) on the same capture — the ~250MB delta is mostly the edges map and its per-edge Strings. Memory stays bounded by max_flows, so this is a constant-factor observation, not a complexity bug.

**Recommendation:** Store the Copy identities on the edge (client_key/server_key: AssetKey, proto: IpProto) and resolve display strings only in the renderers (render_deps, deps_dot, JSON serialization) via the labels map that dependency_edges already builds — or intern labels as Rc<str>/Arc<str> shared between edges touching the same asset. Per-edge memory drops from ~5 Strings (~150-250B) to ~50B; at the 2M-edge cap that is roughly 300-400MB saved with no complexity change.

### [INFO] Table::write_row heap-allocates a padding String per cell via " ".repeat(pad) — tens of millions of transient allocations on cap-scale tables

**Where:** `src/output/table.rs (lines 71-93)` · **Dimension:** perf-scale

Each padded cell allocates a fresh String of spaces and immediately drops it. At the 2M-flow cap an 8-column flows table performs up to ~16M such allocations (one per padded cell) inside the single-threaded render loop. Pure constant-factor allocator churn — O(n) complexity is unchanged — but it is free to remove and this loop is the hottest part of table rendering (part of the measured 2.5s/500k-row render).

**Recommendation:** Use width-parameterized format specifiers, which pad without allocating: `write!(out, "{cell:<width$}")` / `write!(out, "{cell:>width$}")` (note: std pads by char count, matching the existing display_width semantics at table.rs:96-98). Alternatively `out.extend(std::iter::repeat(' ').take(pad))`. Zero allocations per cell.

### [INFO] JSON timestamp strings truncate to microseconds while duration_secs keeps nanoseconds — internal inconsistency for ns-resolution captures

**Where:** `src/types.rs (lines 105-120)` · **Dimension:** reader-equivalence-skew

Timestamp::Display (used verbatim by Serialize at types.rs:122-126) renders `micros = self.nanos / 1000` (types.rs:114), discarding sub-microsecond digits, while Stats::duration_secs (stats.rs:43-48 via secs_since at types.rs:78-85) uses full nanosecond precision. For nanosecond-resolution inputs (legacy-ns magic, legacy.rs:20-21/121-123, or pcapng if_tsresol=9), a JSON consumer computing last_ts − first_ts from the strings can disagree with duration_secs by up to ~2µs in the same document. Microsecond-resolution containers are unaffected, and cross-format equivalence holds wherever the timestamps are µs-representable (verified byte-identical JSON for legacy-µs vs legacy-ns vs EPB on µs-grain data). Cosmetic at mission-critical bar, but worth recording since the crate otherwise guarantees deterministic, format-independent output.

**Recommendation:** Render nine fractional digits (or trailing-zero-trimmed nanoseconds) in Display/Serialize, or document that JSON time strings are µs-granular and duration_secs is the authoritative span.

### [INFO] Process has no signal handler at all; integrity on interrupt rests entirely on default disposition plus output-format self-validation

**Where:** `src/main.rs (lines 3-19)` · **Dimension:** signal-interrupt-output-integrity

Recording the overall posture for this audit dimension: the crate contains zero signal-handling code (no ctrlc/signal-hook dependency in Cargo.toml:38-42, no sigaction — and none is writable in-crate since `#![forbid(unsafe_code)]` rules out raw libc). **Recommendation:** If a handler is ever wanted (e.g., to print 'pincer: interrupted — output incomplete' on stderr before dying, giving log collectors an explicit marker), the `ctrlc` crate is the only forbid(unsafe_code)-compatible route; set an AtomicBool checked in the Pass::run record loop and before emit.
